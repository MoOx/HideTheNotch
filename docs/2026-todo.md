# What is known to be missing

Written down when found, so it is not rediscovered by a reviewer.

Ordered by what it costs to ship without it, not by how hard it is. The first
section is what stands between here and a published v2; the second is what the
app owes its users once it is out; the rest is the workshop.

---

## 1. Before it ships

### Accessibility Nutrition Labels, answered by measurement

App Store Connect asks, per device, which accessibility features the app
supports: VoiceOver, Voice Control, Larger Text, Dark Interface, Differentiate
Without Color Alone, Sufficient Contrast, Reduced Motion, Captions, Audio
Descriptions. It is optional and leaving it blank refuses nothing.

**The bar is higher than it reads.** Declaring a feature asserts that a user can
complete *every* common task with it on, and Apple counts first launch, settings
and support among the common ones, not just the app's purpose. An inaccurate
label is something App Review can require to be corrected, in the label or in
the app.

So it is not a form to fill from memory. `src/ui/a11y.ts` is real work, and it
is narrow on purpose: it turns the two sliders into `adjustable` roles, which is
the right answer for a drag. But accessibility attributes appear in a handful of
components and in none of `Preview`, `MeshEditor`, `Glass` or `FamilyDots`, and
the mesh editor is a drag surface with nothing else to offer. "Every common task
under VoiceOver" is therefore probably not true today.

Two look plausible without any work: **Dark Interface**, since the app is dark by
design, and **Sufficient Contrast**. **Captions** and **Audio Descriptions** do
not apply, there is no video and no audio, and a feature that does not apply is
not one to claim.

**What to do**: run the app on a simulator with each feature on in turn,
VoiceOver, text at 200%, Reduce Motion, and try to reach an exported wallpaper
each time. Answer from what happened. That audit is the work; the form is five
minutes afterwards.

### Sentry

Done, and what is left is the account side.

`index.ts` initialises it and `app.json` carries the Expo plugin.

**What it sends.** Three things arrive without anybody writing code for them,
because the SDK installs the handlers by default: uncaught JavaScript errors,
unhandled promise rejections, and native crashes, which are the only channel
that can report a Skia or Kotlin fault since the process is gone before any
JavaScript could run. `Sentry.wrap` adds a React error boundary above the tree,
so a render that throws is a report rather than a white screen.

Four more are sent on purpose, through `src/report.ts`, and they are the
interesting ones: a handled failure is a path somebody anticipated, in the part
of the app that does the thing the app is for, and until now it ended in an
alert seen by one person who was never going to write about it.

| Tag | When |
| --- | ---- |
| `export.save` | the export could not be rendered or written to the library |
| `export.share` | same, on the way to the share sheet |
| `photo.open` | a chosen photograph would not decode, after every path was tried |
| `cutout.native` | the system refused to describe its own cutout, which is the one measurement everything rests on |

Each carries the recipe, the surface size and the cutout kind, none of which
says anything about anybody. There are no interaction breadcrumbs in this build
(they arrive with tracing, which is off), so that context is what a trail would
have been for. Every report also carries the screen it came from, and
`cutoutFrom` as a tag: the same complaint means a drawing bug from a phone that
measured its own cutout, and a missing row in `models.ts` from one that fell
back to the safe area.

Two things are deliberately not reported: a refused permission, which is
somebody saying no rather than the app failing, and the capture harness's own
file reads.

**What it does not send.** Session replay, performance tracing, PII, console
breadcrumbs, and any string shaped like a file path, which `beforeSend` replaces
on the way out. Each of those is also a line that would otherwise have to be
declared in App Privacy and in Data safety, and defended in the privacy policy.

**The one thing still needed is the token.** `SENTRY_AUTH_TOKEN`, from
[sentry.io/settings/moox/auth-tokens](https://sentry.io/settings/moox/auth-tokens/),
under Organization Tokens rather than as a personal one. There is no scope to
choose: an organisation token carries `org:ci` and nothing else, which is the
scope Sentry made for this and covers creating a release and uploading source
maps. The per scope checkboxes belong to personal tokens, which is a different
kind of token and the wrong one here.

It is used at build time and never at runtime, so a build without it succeeds
and its crash reports arrive minified, which is most of their value gone.

It goes in two places:

| Where | How |
| ----- | --- |
| This machine | `SENTRY_AUTH_TOKEN=` in `.env`, which fastlane loads. See `.env.example` |
| GitHub Actions | repository secret `SENTRY_AUTH_TOKEN`. Both release workflows already pass it through |

There is no third place, and that is settled rather than pending: putting it
under `secrets/` in the certificates repository was tried and reverted, because
that directory is for material you cannot cheaply re-create and a Sentry token
is regenerated in a minute. It is declared in `.env.example` as optional, so
`fastlane doctor` reports whether it is set. See section 8.4 of
`docs/08-open-decisions.md` in that repository.

**Nothing has been built with it yet.** It adds a native dependency, so the next
`expo prebuild` is the first real test. The DSN can be proven before that, from
a terminal and without the app:

```sh
npx sentry-cli send-event -m "hello from the terminal"
```

If that appears in the Sentry project, the DSN, the organisation and the token
are all right, and what is left to prove is only that the app is wired to them.

### The captures are stale, and now they are also not committed

`npm run deck` fails by design, because `marketing/captures/*/*/05-compare.png`
does not exist: the before and after slot moved into the app and nothing has been
recaptured since. No captures, no screenshots, no listing.

Two things changed under them since:

- **They are no longer in git.** They are output, a hundred and fifty megabytes
  of it, replaced wholesale by every run. `renders/` was already ignored and
  these were not, which was the inconsistency. Anyone composing a deck runs
  `npm run captures:ios` and `npm run captures:android` first, and `npm run deck`
  says exactly that when they are missing.
- **The Android emulator is given a real punch hole**, through the AOSP overlay
  the "Display cutout" developer option switches between, instead of the app
  being told to pretend through a device preset in the URL. The status bar is
  laid out around a hole that is really there, and the app finds it the way it
  finds one on a phone.

  **The overlay it asks for was wrong, and has been corrected.** `hole` is a
  punch hole in the top left corner, not a centred one, so the app masked the
  corner while the deck drew its hole in the middle of the same picture. The
  centred one is `emu01`, 479..601 x 0..132 on this screen, and it is also what
  an API 35 image reports with no overlay at all. Expect `==> cutout emu01`,
  then a centred punch hole in every shot. If the system image turns out to have
  no such overlay the run stops and says so, rather than producing a deck of an
  app hiding nothing.

### Where the deck comes from, now that the captures are not in git

The question this raised is the right one: if the captures are not committed, how
does a release get its screenshots? The answer, checked rather than assumed, is
that committing them never fed a release in the first place.

The chain is captures, then `npm run deck` composes them into
`marketing/renders/`, then `listing.cjs` copies that into the two metadata trees
fastlane uploads. **`renders/` has always been git ignored**, and no workflow has
ever run `npm run deck`. So every CI upload so far has written the text and found
no images. Play leaves a listing's images alone when the tree does not mention
them, which is why nobody noticed.

Two ways forward, and they are not exclusive.

**The visuals go up from this machine**, which is what happens today. `npm run
captures:*`, `npm run deck`, look at them, then `fastlane ios metadata`. The CI
ships binaries and text. Composing a deck means looking at it before sending it,
so a human step is not obviously the wrong shape.

One trap closed on the way: `upload_to_app_store` runs with
`overwrite_screenshots: true`, so running that lane with an empty
`marketing/renders/` would have **deleted** every screenshot on the App Store
record and replaced them with nothing. On a fresh clone that was one command
away. `listing.cjs` now refuses to write a listing with no deck at all, and
`HTN_TEXT_ONLY=1` says it was meant.

**Or the captures are taken in CI.** `.github/workflows/store-captures.yml` does
exactly that: a macOS runner builds for the simulator and photographs six
languages, an ubuntu runner does the same on an emulator with KVM, and a third
job composes both decks. Everything comes back as an artefact.

That file already existed and was deleted on 31 August, having never run: every
one of its runs is `skipped`, because it asks for a `[captures]` marker in the
commit message and none carried one. It is restored here with the two things
that had gone stale fixed, the artefact paths (captures live under a language
directory now) and the emulator's cutout.

**What it costs: nothing but time.** The repository is public, so the hosted
runners are free, macOS included. Reckon forty to fifty minutes of wall clock,
the two halves in parallel, most of it the two release builds. For comparison,
`verify.yml` takes five.

**Where the pictures end up.** As run artefacts, three of them: `captures-ios`
and `captures-android`, kept a week because they are an intermediate, and
`store-deck`, kept the default ninety days because that is what a listing
uploads. Inside the run the deck job downloads the first two with
`actions/download-artifact` and composes them, which is the only handover that
happens by itself.

Outside the run, nothing collects them, and that was the missing half:
`npm run deck:fetch` is it. It finds the last successful run, prints the commit
it was built from, and drops the deck into `marketing/renders`, which is exactly
where `listing.cjs` looks. `HTN_WHAT=captures` takes the raw captures instead,
for recomposing locally after editing `shots.json` without either toolchain.

So the release path is CI for the pictures, this machine for the upload:

```sh
npm run deck:fetch
npm run marketing:serve      # look at them
bundle exec fastlane ios metadata
```

What is still not automatic is the last line. Having a release workflow upload a
deck built by a different workflow run means tying the two together (a
`workflow_run` trigger, a `gh run download` by run id inside the lane, or the
deck published as a release asset), which is a decision rather than a line of
YAML. It is also the step where somebody should be looking at the pictures, so
it is not obviously a step to remove.

### iPad screenshots: the strict minimum, and nothing more

`supportsTablet` has to stay `true` (Apple refuses an update that drops a device
family, `90101`), so the App Store record wants screenshots on the iPad slot.
Not because the app is good on an iPad. Because v1 was published there.

**So this is a formality, and it should be treated as one.** The app runs on an
iPad, draws a gradient with a black band across the top, and says nothing it
cannot back up: there is no cutout on an iPad and it does not pretend there is.
It is a phone layout stretched over thirteen inches. That is the truth of the
situation and it is not worth a design project.

A raw capture would have been enough: an iPad Air 13 inch simulator writes
2048 x 2732, a valid size for that slot, and `deliver` sorts screenshots by
resolution rather than by filename, so untouched captures would have landed
there by themselves. It goes through the deck anyway, because one app with two
ways of making its screenshots is one way too many, and because this pipeline is
meant to be lifted into another project.

**The pipeline is wired, and the settings are not.** `npm run captures:ipad` and
a third `compose` call in `npm run deck` exist, `marketing/shots-ipad.json` is a
copy of the iPhone spec with three things changed, and `listing.cjs` now merges
several render directories into one listing so the phone deck and the iPad deck
sit side by side on the same version.

What is genuinely iPad in that spec: the canvas at 2048 x 2732, the cutout set
to `none` because an iPad has none, and captures read from
`marketing/captures/ipad`. Everything else is the iPhone's, on purpose, and
everything else is what wants an eye. A first composition showed exactly which:
`scale` and `drop` put the device too low and too large, the frame's proportions
crop the app's right hand controls, and the seal lands in the middle of the
screen. All of it is spec values, none of it is code.

Nothing in `capture-ios.sh` was iPhone specific: the device and the output
directory were already variables, and the simulator build is a universal binary.

### Later: the deck, per store or per platform

Worth settling before the file layout grows a third copy of everything, and
worth knowing that neither "per store" nor "per platform" is quite the shape.

**A listing is a store and a platform together.** On App Store Connect an app
record holds one metadata set per *platform*: iOS and macOS are separate, each
with its own version, description, keywords and screenshots. iPadOS is not one
of them, it is extra screenshot slots inside the iOS listing. Play has one
listing for Android, with several screenshot types inside it.

So:

| | Text | Screenshots |
| --- | --- | --- |
| App Store, iOS | one set | iPhone 6.9, iPad 13 |
| App Store, macOS | its own set, if a Mac app ever exists | Mac sizes |
| Play, Android | one set | phone, and tablets if declared |

Which means the texts are per store and per platform, and the screenshots are
per device family. Today `listing.json` holds one text for both stores, with
the four fields that exist on only one of them (`subtitle`, `keywords`, `promo`
for Apple, `short` for Play) sitting beside the shared ones. That is the right
shape and it should survive: the whole point is that the two stores say the same
thing.

What should change is the deck specs. `shots.json` and `shots-play.json` are
named after stores but are really named after device frames, and each carries a
full copy of the caption text in six languages. A third file would make three
copies of the same sentences. The shape that scales is one spec per device
family, named for it, with the captions referenced from a single place rather
than repeated:

```
marketing/decks/iphone.json     1320 x 2868, island frame
marketing/decks/ipad.json       2048 x 2732, no cutout
marketing/decks/android.json    1080 x 2400, punch hole
marketing/decks/mac.json        if it ever exists
marketing/captions.json         the six languages, once
```

Nothing in `compose.cjs` resists this: it already reads its device metrics from
the spec, which is how the Play deck draws a Pixel, and it already handles
`cutout.shape: "none"`, which is what an iPad and a desktop screenshot need.

**On macOS specifically.** A MacBook has a notch, so the idea is sound, but
there are two very different versions of it and only one costs anything. Making
the iPad app available on Apple Silicon Macs is a checkbox, and Apple then lists
it using the iOS metadata and the iPad screenshots: no new text, no new
pictures. A real Mac app that draws a wallpaper for a MacBook display is a
separate platform on the record, a separate version, a separate build, its own
description and its own screenshots, and `deliver` uploads it as `platform:
"osx"`. The first is free and pointless. The second is a project.

### The privacy policy page

`marketing/listing.json` points every locale at
`moox.io/apps/hide-the-notch/privacy`. Both stores check that it answers. Sentry
makes this page's content a real question rather than a formality: it is the one
thing in the app that sends anything anywhere.

### Play may want 12 testers for 14 days before it allows production at all

Not a task, a date. Google requires a **personal** developer account **created
after 13 November 2023** to run a closed test with at least **12 testers opted
in continuously for 14 days** before production access is granted. Accounts
older than that, and organisation accounts, are exempt.

Which case this account is in decides whether v2 can go out this week or in a
fortnight, and Play Console is the only thing that can say: if the requirement
applies, the Production track is disabled and the dashboard counts the testers
and the days. Worth looking now rather than on the day, since nothing in this
repository can shorten fourteen days.

The internal track does not count if it applies: it has to be a closed test.
Nothing here changes for that, `npm run beta:android` already uploads where a
closed test reads from.

### App Privacy and Data safety

Two questionnaires, one per store, neither reachable through an API. The honest
answers are short (nothing leaves the device but crash reports) but they still
have to be given, and they have to match what Sentry is configured to send.

### The copy is a first draft

Six languages written in one pass, five of them by someone who does not speak
them. `npm run marketing:serve` then [`/listing`](http://localhost:4321/listing)
shows every string against its limit, which is the place to read them.

The two platform specific strings are the ones to read first: `exportHintIos`
names Settings and Wallpaper, because every iPhone has exactly one of each;
`exportHintAndroid` names no path at all, because every manufacturer moves it.
Both say the thing that actually matters, which is that nothing may crop or zoom
the picture.

## 2. What the app owes its users

### Remember what was set

Killing the app throws away everything: the imported photo, the effect, the
slider, and a gradient that was moved by hand. Coming back to adjust one thing
means doing all of it again, which is the difference between a tool and a toy.

It is one object of parameters and it costs nothing: the recipe (source, mask,
framing) plus the chosen family, written on change and read at launch. The photo
needs its URI kept and re-checked, since the picker hands out references that can
go stale.

It is also what the rating prompt below needs, since a count of exports has to
survive a launch.

### Ask for a rating, then offer the tip jar

In that order and independently, because the second cannot be made to depend on
the first.

**Read this first: a donation is not a purchase.** The section further down was
written assuming three consumable in-app purchases. It is the road not taken.
What ships instead is what Saracroche does, which is the same thing on both
platforms: a row that opens a small sheet, and buttons in it that each open a
payment page in the browser, a card page, PayPal, Liberapay. Nothing about
payment happens inside the app.

Whether that is allowed took some looking at, because the answer changed in 2026
and because the first thing you find says it is not.

**iOS: allowed, and it is the prescribed route.** Guideline 3.2.1 says an app
that is not an approved nonprofit may not collect funds inside the app at all,
and that money for such causes has to be collected outside it, through Safari or
SMS. The link out is not a way around in-app purchase, it is what the rule asks
for. Apple takes no commission and the listing carries no "In-App Purchases"
badge.

**Android: allowed too, on two independent grounds**, neither of which is the
donation clause.

The first is that Play billing is required for purchases of in-app digital
content, and a donation is not one. It buys nothing, unlocks nothing, grants
nothing. This is the load bearing point, and it is also the fragile one: the
moment a tip unlocks, grants or thanks with anything at all, it becomes a
purchase and Play billing is mandatory. Whatever is built here must give the
giver strictly nothing but the fact of having given.

The second is that the anti-steering rule that used to forbid leading users to
another payment method has been dismantled. The Ninth Circuit upheld the Epic
injunction on 12 September 2025, Google stopped requiring Play billing and
stopped forbidding external links for US users on 29 October 2025, and external
links to transactions are permitted across the US, the UK and the EEA as of mid
2026. France is in the EEA.

**The trap, and it is worth knowing precisely.** Play's Payments policy has a
clause for "tax exempt donations", and reaching for it is what gets an app
removed. AnkiDroid is living through exactly that right now: its link to Open
Collective was refused, its fiscal host's 501(c)(6) determination was rejected
because Google reads that clause as meaning a public benefit charity, and it has
until 11 September 2026 to ship a build without the links or come off the store
([ankidroid/Anki-Android#21656](https://github.com/ankidroid/Anki-Android/issues/21656),
opened 29 August 2026 and still open).

The lesson is not "donation links are banned". It is that **framing the thing as
a charitable donation to an organisation is worse than framing it as supporting
the person who wrote the app**. AnkiDroid raises money for an entity through a
fiscal host, which is what puts it inside the charity clause and under a test it
cannot pass. A row that says the author would be glad of a coffee invokes none
of that.

So, concretely, for this app: no organisation, no charity, no tax receipt, no
suggestion that anything is deductible. Nothing given in return. The payment
page opens in the browser rather than in a webview with a form in it. And the
AnkiDroid thread is worth watching until it resolves, because it is the only
live reading of how Google reasons about this today.

**What it needs**, once that is settled: a page on `moox.io` with Stripe, PayPal
or Liberapay behind it, a row in the export sheet, and the sheet itself, which
the app already knows how to build. Same shape on both platforms.

**The store copy and the screenshots have to match the build.** The listing
mentions no tip at all, in any of the six languages. The deck's last slot, the
card reading "the only possible purchase is a tip", is set aside until the row
exists, since metadata describing something the app does not do is Apple's
guideline 2.3.1. The seal on the first slot stays: "pourboire bienvenu" says a
tip would be welcome, which is true of any free app and describes no mechanism,
where the card described a purchase.

The rating goes on the **second** export, never the first: the app has just done
the thing it exists for, twice, which is the only moment a prompt is not an
interruption. `expo-store-review`, `StoreReview.isAvailableAsync()` then
`requestReview()`.

Nothing comes back from that call. Both APIs are opaque on purpose: the system
decides whether to show anything, and reports neither that it did nor what was
tapped. Apple caps it at three prompts a year per device, Google keeps its own
quota to itself. Asking people first and only prompting the happy ones is
forbidden rather than merely impossible.

The **tip jar** is therefore its own thing, offered calmly and to everybody:
three consumable amounts, unlocking nothing. Both stores require it to go through
their billing (Apple's 3.1.1, Google's payments policy), so a web link or Stripe
is not an option. Apple recognises tips explicitly and asks that they stay
consumable and unlock no functionality, which is what we want anyway. Prices come
from each store's price points rather than being typed in, and the commission is
15 percent on both up to the first million, on Apple's side only after enrolling
in the Small Business Program.

Three consumables, around one, five and ten euros:

| | Product | Roughly | What the author actually gets |
| --- | --- | --- | --- |
| a coffee | `tip.coffee` | 1 to 1.19 EUR | about 0.84 EUR |
| a round | `tip.round` | 5 to 5.49 EUR | about 3.90 EUR |
| a good evening | `tip.evening` | 10 to 10.99 EUR | about 7.80 EUR |

The third column is the point of the table: in the EU both stores are the
merchant of record, the price shown includes VAT, and the commission comes off
what is left. At 20 percent VAT and 15 percent commission a 1.19 tip is 0.84.

The two stores will not agree on the exact figures and should not be made to.
Apple picks from a grid of price points, chosen once in a base region and derived
everywhere else; Play takes a price per country between a floor and a ceiling, so
round numbers are possible there and not always here. Read the actual grid in App
Store Connect rather than trusting a tier number remembered from before the 2023
overhaul. And never print an amount in the app: both billing APIs hand back a
formatted, localised price string, and that string is the only correct one.

**Where.** Its own section in the export sheet, between Export and the app's own
rows: two lines, write a review and leave a tip. Both are the same idea, one
costs nothing and the other does, and putting them together is what makes the
second one read as a thank you rather than as a sales pitch.

Not called "Support us", tempting as it is. The section below it already has a
row called Support meaning *get help*, and the two would sit three lines apart.
Something like "If it helped" instead, in six languages, and the help row keeps
its name.

**The prices come from the store, and they are shown.** "Never print an amount"
means never write one in `src/i18n`, not hide it. The billing API returns, per
product, a **formatted localised price** for the viewer's storefront: `1,19 €`,
`$1.29`, `¥200`, right currency, right separator, right side of the number. So a
row reads `Un café` from our translations and `1,19 €` from theirs, and nobody in
Japan is quoted euros.

Two consequences. That list is **fetched, asynchronous, and can fail**: offline,
a product not yet approved, a sandbox in a mood. The row stays tappable and the
fetch happens on the tap; if it fails, one alert saying to try again on a better
connection, and nothing else. A row greyed out for reasons nobody can see is
worse than a row that explains itself once. And the **order is ours**, from our
own array, since nothing guarantees the order the store answers in.

The three amounts open in a **bottom sheet**, the same one the rest of the app
uses. Three rows, a line of thanks, and no illustration.

The stores also hold a title and description per product, per locale. Not worth
using: it would mean maintaining six languages in two consoles instead of one
file. Our label, their price.

**The review row is not the prompt.** `requestReview()` is for the automatic
moment and may legitimately show nothing at all, so behind a button it is a
button that does nothing, which is worse than no button. Apple says as much. A
row the user taps deep links out instead: `StoreReview.storeUrl()`, which needs
`ios.appStoreUrl` and `android.playStoreUrl` in `app.json`.

**When.** The automatic rating prompt stays on the second export. The tip needs
no moment at all, since it has a place. At most one nudge on top, once ever, on
the tenth export. Not every ten: a repeat ask for money is the definition of
nagging, and it would fall hardest on the people who use the app most, who are
exactly the ones who liked it. Two flags in storage, tipped and nudged, either
one ends it for good. Never in the same session as the rating prompt: asking for
a favour and then for money is a toll booth.

The module is the open question: `expo-in-app-purchases` was discontinued, and
what replaces it (`expo-iap`, `react-native-iap`) wants checking against the SDK
in use at the time rather than picking from memory.

Both stores stamp a listing that has any purchase with a badge, so the copy has
to say plainly that the tip is optional and unlocks nothing, in the same breath
as "free". See
[`2026-store-marketing-automation.md`](2026-store-marketing-automation.md),
section 11.

### Setting the wallpaper in one gesture

Today the app saves a picture and then tells you where to go and what not to let
the system do to it, in six languages, differently on each platform. That
sentence is the seam: everything up to it is the app's, and everything after it
is a hope.

Both platforms can close it, and both need native code. iOS has no API to set a
wallpaper, so the nearest honest thing is an App Intent and a shortcut, which
puts it one tap away rather than five. Android has
`WallpaperManager.setBitmap()`, which does exactly the thing, home screen and
lock screen, with a permission that is granted by using it.

It is the largest single improvement left, and the one that would make the
export hints unnecessary on Android.

### The families that were promised

Three families ship: bar, stripes, fade.
[`2026-feasibility-and-ui.md`](2026-feasibility-and-ui.md) designs seven, and
the four that are missing are 07 (hanging object), 08 (organic decor), 09
(content camouflage) and 12 (generative).

Family 12 is the one with a debt attached. That same document cuts v1's bundled
wallpaper library, and justifies it with "family 12 replaces it with an endless
generator that weighs nothing". Family 12 does not exist, so what actually
shipped is six fixed gradients and a mesh editor. For anyone who does not import
a photograph, the choice is narrower than v1's, which is the opposite of what
the reasoning claimed. Either the family arrives, or that paragraph should stop
promising it.

The cheap half of it is a shuffle: the gradients are mesh points and
`presetSource` already builds one, so moving the points at random is a few lines
and gives back the endlessness the argument was based on. The real family 12 is
a bigger piece of work.

### A library to browse, rights free

Wanted, and further out than the rest of this section. Not v1's bundled bank
back, which was heavy and dated the moment it shipped: a browser onto something
like Unsplash, where the picture is chosen rather than shipped.

The reason it belongs here rather than in the workshop is that it answers the
same question the families do. Someone who arrives with no photograph in mind
currently gets six gradients, and a gradient is a shape, not a place. A picture
of somewhere is what most people actually put behind their phone, and the app
has no way to offer one.

What it needs, roughly in the order it would be met: an API key and the terms
that come with it (Unsplash asks for attribution and for a download to be
reported back, Pexels and Openverse have their own), a network permission this
app has never declared, a search field and a grid, which is more interface than
anything here has, and a rule for what happens offline. The rendering side is
free: a downloaded file is a photograph like any other and `useSourceImage`
already opens it.

The rights question is the one to settle first, because it decides the source.
"Free to use" is not the same as "free to redistribute inside an app", and the
one thing this app must never do is put somebody in front of a licence they did
not read.

### The rest of the accessibility pass

The two controls that had nothing are done: the wallpaper announces itself as an
adjustable that pages between effects, and `VSlider` as an adjustable that moves
its value a tenth at a time, which is the same notch the haptics give. Both
because a drag is a gesture a screen reader has already taken for itself.

Whether a blind user wants to judge a wallpaper is beside the point. Making one
is a reasonable thing to want: the cutout is real whether or not it is seen, and
someone may well be making it for a phone that is theirs, or for somebody else's
eyes. Pick an effect, set how far the black reaches, save it: three controls, all
three reachable now.

What is left is smaller and worth doing next time the files are open:

- `MeshEditor` has labels on its buttons but its points are draggable and nothing
  else. An adjustable per axis, or a set of actions on the selected point.
- The sheets come from `@expo/ui`, so the system labels their rows, but the
  thumbnail bands inside them (`Thumbs.tsx`) are pictures with a label attached
  and could say which one is selected more clearly.
- Nothing has been tried under VoiceOver or TalkBack on a real device yet. The
  code is right; that is not the same as it working.

## 3. The workshop

### The release tag: done, and it is the trigger

The tag was never going to be written after an upload, and that is what makes the
"too many working releases" problem disappear: **both release workflows already
fire on `refs/tags/v*`**. The tag is the cause of a release, not its record.

So there are two ways a build goes out, and only one of them leaves a trace:

| | How | Leaves a tag |
| --- | --- | --- |
| Working build | `[testflight]` or `[play]` in a commit message, or a manual dispatch | no |
| Release | `npm run release`, then push the tag | yes, one per version |

`tools/release.cjs` is the gate. It refuses a dirty tree (the commit tagged has
to be the commit built, since its SHA is stamped into every crash report), a tag
that already exists, a version that has not gone up, and, the useful one, a
release note identical to the previous tag's. That note is
`locales.*.release` in `marketing/listing.json`, nothing else reminds anyone to
change it, and it is what both stores show as What's New.

The workflows now also refuse a tag whose number does not match `app.json`.

There is **no per store tag**, because a version is published once even though
the two stores count builds separately, and `stamp_commit!` already ties any
build back to its commit.

**Promotion is two lanes and two workflows.** `fastlane ios release` takes the
last TestFlight build, attaches it to the version and uploads the copy and the
deck with it, because App Store metadata belongs to a version rather than to the
app. It stops there: `SUBMIT_FOR_REVIEW=1` is what starts a review, since a
review is not something to begin by accident. `fastlane android release`
promotes the highest internal version code to production, so what ships is the
artefact that was tested rather than a rebuild, and `PLAY_ROLLOUT=0.1` hands it
to a tenth of users first.

Both are reachable three ways: `npm run promote:ios` and `npm run
promote:android` here, or the **iOS to the App Store** and **Android to
production** workflows, which are forms in the Actions tab and compile nothing,
so a release needs a browser and not a laptop.

Neither has been executed against a store yet, which is the one thing to be
careful about. fastlane loads and lists them, and `npm run doctor` reports the
environment they need; what nothing has exercised is what they do when they
reach App Store Connect and Play. Read the first `npm run promote:ios` line by
line before believing it, and leave `SUBMIT_FOR_REVIEW` out of that first run.

**Which is why v2 does not ship from a tag.** A tag that starts a release
assumes the release works, and that assumption has never been tested here: the
iOS build can fail, the Android build can fail, the review can come back
rejected. So the first one goes out by hand, in the order the README sets out,
and the tag is written at the end as a record. Pushing it re-runs both build
workflows against a commit whose release is already done, which is the cheapest
way to find out whether CI can do the same. The order flips once it has.

`tools/fastlane.sh` is what every `npm run` reaching fastlane goes through: it
installs the gems on first use, into `vendor/bundle` rather than into the Ruby
installation, so a fresh clone needs `npm install` and nothing else even to
ship. v1 did this from `postinstall`, which charged a minute of gem
installation to everybody including everybody who was never going to ship.

It also sets a UTF-8 locale when the shell has none, which is not housekeeping:
fastlane warns about it, and the reason is that Ruby reading `ja/description.txt`
under `LC_CTYPE=C` produces bytes it cannot encode back. That uploads a listing
as mojibake, in the two languages nobody proofreading an English App Store page
would look at.

All of this went upstream and came back: `fastlane/`, `.env.example` and the
four workflows are now copies of the templates in `MoOx/certificates`, and the
only line of the Fastfile that is ours is `stamp_commit!`. Fix anything else
there rather than here.

One idea of ours was rejected on the way, and the replacement is better. The
Fastfile briefly read the bundle identifier and the package name out of
`app.json`, on the grounds that Expo generates both native projects from that
file. The template instead declares every value in `.env.example`, with an
`@needed` line naming the lanes that require it, checks the whole list before a
lane does anything, and reports it through `fastlane doctor`. That works for a
project that is not an Expo one, tells you about four missing values at once
instead of one per failed run, and keeps `app.json` for the version alone, where
`APP_VERSION` can still override it.

What belongs upstream, in the certificates templates rather than here: the
tag-matches-version guard is the same three lines in every app, and so is the
Sentry token. A prompt for that repository has been written.

### Draft: `npm run deploy`, one interactive pass over a release

A sketch, not a decision. Written down while the shape of a release is fresh,
because the first few are being done by hand and by hand is where the questions
show up.

The idea is one console program that walks a release and asks what it cannot
work out for itself. Which platforms, iOS, Android or both. Whether to create
the version. Whether the captures need retaking, and the deck recomposing.
Whether the store copy is up to date. Whether to push the metadata on each side.

**What would make it worth writing is the checking, not the asking.** A wrapper
that only asks questions is a worse README. The value is in the answers it can
find on its own and put in front of somebody before they commit to anything:

| Question | Answered by |
| -------- | ----------- |
| Is the environment complete? | the same manifest `fastlane doctor` reads |
| Is there a build on TestFlight, and has it finished processing? | App Store Connect |
| Is there a version open for editing, and is it the one in `app.json`? | App Store Connect, and this is the trap that cost an afternoon |
| Is there anything on the Play internal track to promote? | the Play API |
| Are the captures still of this interface? | `marketing/captures/*/.fingerprint`, with the caveat below |
| Is there a composed deck? | `marketing/renders` |
| Has the release note changed since the last tag? | `git tag -l --format` against `marketing/listing.json` |
| Does `app.json` say a version that has not shipped? | the tags |

Then two questions it must never answer by itself, because they are the two that
cannot be undone quietly: submit for review, and the rollout fraction.

**One of those rows deserves better than a yes or no, and it is the captures.**
The fingerprint is not a commit hash: it hashes the content of the eight paths
that decide what a screenshot shows, comments stripped, and `marketing/listing.json`
is not among them, so editing store copy does not mark anything stale. But
`src/i18n/strings.ts` is, and rightly, since a string can appear on a captured
screen. The result is a signal whose two answers are worth very different
amounts. Green means nothing that could matter has moved, and the whole question
can be skipped. Red means something that could matter has moved, which is not
the same as "the pictures are wrong", and a wording change in a screen nobody
photographs will produce it.

So red should not become a question. It should become a look: put the captures
up next to what the app renders now, all of them, all six languages, and let the
eye decide in two seconds. That is the contact sheet already sitting in phase 2
of the workbench, and `npm run marketing:serve` is half of it already, since it
composes the deck live from the current code and can shoot any slot for real
beside it. The deploy program should open that rather than ask.

Narrowing the fingerprint per shot is the other option and it is not worth it:
knowing which strings each shot renders means teaching the hash what the app
draws, which is the app's job and not a checksum's.

**Three rules, if it gets written.**

It prints the command it is about to run, every time. An interactive wrapper
that hides which lane failed turns a readable fastlane error into a mystery.

It is resumable and idempotent. A release fails halfway more often than it
succeeds outright, and answering eleven questions again to retry one step is how
a tool stops being used.

It is never the only way in. `npm run beta:ios` and the rest stay exactly as
they are, and `deploy` calls them. Anything it can do, a person can do without
it.

**The open question** is where it would live. Most of the checks above are this
project's, but the shape of them is every project's, and the same argument that
moved the lanes into `MoOx/certificates` applies. Probably: write it here first,
against a real release, and see what is left that is not specific to this app.

### `ios metadata` fails unhelpfully on an app with no open version

Worth sending upstream, because every app meets it once, on its first release.

`deliver` only creates or renames a version when `app_version` is given, and the
template's `metadata` lane deliberately gives none, so that a correction lands on
whichever version is already open for editing. On an app that has no open
version, that turns into `Cannot find edit app store version` retried six times
over about five minutes, and then a failure that says nothing about what to do.

The fix is a preflight in the lane: ask for the edit version once, and if there
is none, stop immediately with the two ways out, run `ios release` or add the
version in App Store Connect. Ten lines, and it belongs in
`MoOx/certificates` rather than here.

The reading behind it, from fastlane 2.238.0:
`deliver/lib/deliver/runner.rb:29` gates `verify_version` on `app_version` being
set, and `spaceship/.../models/app.rb:215` is where `ensure_version!` posts a new
version when none is open.

### The repository is heavy, and the history keeps it that way

`.git` is around 480 MB. The captures are out of the tree now, but the blobs are
still in the history of this branch: 94 MB of files over one megabyte in the last
two commits alone.

`main` is still at v1, so **nothing of this is in `main` yet**. That is the
window. Squash merging this branch means `main` never receives those blobs at
all, and GitHub collects them once the branch is deleted. A merge commit carries
the whole history in, and then only a rewrite gets it out.

Nothing to do in the tree; it is a decision to make when this lands.

### What "quality control" means here, and where it stops

`npm run verify` is genuinely good, and it is worth being precise about what it
covers, because the gap is not obvious from the outside. It runs the real drawing
code against CanvasKit over four geometries and reads the pixels back: absolute
black under the cutout, a fade that is really dithered, no banding in the steep
part, and a demo script that fits inside Apple's App Preview window. Every one of
those is a property that would ship broken and unnoticed otherwise.

What nothing covers is the layer above the pixels, all of it pure functions with
no device in sight:

- `clampFraming`, which decides where a pinched photo is allowed to sit. Push a
  zoom against either end and the picture should stop, not slide.
- `resolve()` in `useGeometry`, the three layer fallback (system, then the model
  table, then the safe area). The table is what ages: it is correct as far as the
  iPhone 17 and the Air, and every September it quietly stops being complete.
  Nothing fails when that happens, which is the point of the fallback and also
  the reason nobody would notice.
- `slider()` in `App.tsx`, which maps each family's one setting onto zero to one.
  A wrong bound there is a control that cannot reach its own floor.

That is a handful of plain assertions in the existing harness (`tsconfig.harness`
already compiles `src/` for Node), not a test framework. `npm run verify` is the
place: it already runs first in CI.

`npm run lint` is new, and deliberately narrow: correctness rules only, with
every switched off rule carrying its reason in `.oxlintrc.json`. The two
`eslint-disable` comments that used to sit in `App.tsx` referred to a linter that
did not exist; one is now a real dependency the effect declares, and the other is
gone with the code it guarded.

One more thing nothing checks: whether the app still launches. `verify.yml`
bundles for both platforms, which catches an import that does not resolve, and
`store-captures.yml` is the first thing in this repository that runs the real
app, on both platforms, and fails if it does not reach a known state. That makes
it a smoke test that happens to produce pictures, which is a good argument for
running it more often than a deck is needed.

### The capture harness lives in the shipped app, on purpose

`hidethenotch://demo` plays the script and `hidethenotch://shot/03-home` walks
into one of the deck's states, in a release build. That is the whole capture
pipeline: no debug flag, no UI automation, no separate binary, and the build
being photographed is the build that ships.

The one thing that was actually a hazard is gone: the URL used to be able to name
a **file path**, which the app then opened. It was dead code (both platforms use
the bundled photograph) and it was the only place where a public URL scheme could
point the app at something on the device. The URL now carries a shot id and
nothing else.

What is left is a link that can put the app into a known state. Any web page can
do it, and the worst it achieves is a sheet nobody asked for. That is acceptable
and it is the price of a capture pipeline that photographs the real build. If it
ever needs closing, the closure is a shared secret in the URL rather than a debug
flag, since a debug flag would mean the photographed build is not the shipped
one.

### Upstream, when the queue is clear

**Send `contentModifiers` upstream.** It is in
`patches/@expo+ui+57.0.9.patch`: `BottomSheet` gains modifiers for the container
the children are laid out in, where one replaces the derived modifier of the same
type rather than adding to it. It exists because the sheet's own content padding
was unreachable on Android, and because `modifiers` already means two different
things on the two platforms, the content on iOS and the `ModalBottomSheet` itself
on Android. It is additive, nothing that does not ask for it behaves differently,
and it is held here only because there are already pull requests open at
`expo/expo`.

**`requiredWidth` has to go upstream, it cannot be patched.** The thumbnail band
is inset sixteen points from its card on Android instead of reaching its edges,
because Material's `ListItem` pads its content and exposes no prop for it,
Compose has no negative padding, and `Modifier.width` coerces into the
constraints a parent hands down. The one modifier that ignores them is
`requiredWidth`, which `@expo/ui` does not expose.

Registering it in `ModifierRegistry.kt` and patching that file does nothing, and
it is worth knowing why before anyone tries again: the package ships its Android
half as a built `.aar` under `local-maven-repo`, and `expo-module.config.json`
names that as the artifact. The Kotlin sources sitting beside it are never
compiled by this project, so no `prebuild` and no amount of clearing caches will
pick a change up. The pull request should add the modifier and its TypeScript
helper together.

**Android is still looser than iOS.** Three insets stack in a sheet there and the
patch above only reaches the first. `FieldGroup` pads its lazy column by sixteen
and `FieldGroup.Section` spaces its rows by twenty four, both applied inside
components that take no prop for it, and Compose has no negative padding to undo
them with. The thumbnail band works around its own by measuring and offsetting,
see `Thumbs.tsx`; the rest would need the same treatment, more props upstream, or
living with it.
